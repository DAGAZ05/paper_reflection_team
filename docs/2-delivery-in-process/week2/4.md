# 项目设计论证

## （一）选题依据

### 1. 研究意义与问题背景
本项目面向学术论文的多智能体评审场景：各审计组以统一的 API 契约输出结构化评语，反思评估组负责对这些输出进行汇总、裁决与生成最终报告。在这一链路中，系统可信度不取决于“能生成多少评语”，而取决于评语能否被追溯、能否被复核、能否在论文原文中找到支撑证据。换言之，“**评语是否可被证据化**”是学术评审场景的硬约束。

如果上游审计 Agent 生成的 `evidence_quote` 并非来自论文原文，或者引用位置发生错配（例如把方法段落的描述误指到实验段落、把表格数值误当作正文叙述、把图注内容当成结论论据），那么下游的加权裁决与报告拼装就会在错误证据上“越算越真”。这种错误具有链式放大特征：一方面会引发学术诚信层面的风险（对作者做出缺乏证据的否定性判断，损害评审公信力），另一方面会造成工程层面的不可用（前端无法根据 location 高亮跳转，接口契约形同虚设），并最终转化为协作与成本问题（团队不得不把大量时间投入到人工复核，抵消自动化评审带来的效率收益）。因此，证据验证并不是“锦上添花”的后处理，而是多 Agent 评审系统可解释性与可审计性的基础设施。

与此同时，多审计组的输出在现实联调中往往存在明显冗余：同一类通用问题（例如“补充实验设置细节以增强可复现性”“明确符号定义”“补充对比实验”）可能在不同组、不同 wording 下重复出现。如果将这些条目原封不动地汇总到最终报告，会形成“信息噪声盖过关键问题”的阅读体验，降低导师与作者的决策效率。基于此，本模块还需提供建议去重能力，在不丢失来源可追溯性的前提下对语义相近建议进行聚类归并，使最终报告更聚焦、更可执行。

### 2. 国内外相关研究梳理与动态
围绕“证据可追溯的自动化评审/事实核验”，学术界与工业界的研究路径大体可归纳为三类。

第一类是以字符串为核心的匹配与近似匹配（Exact/Fuzzy Matching）。其典型做法是对文本做规范化（大小写、标点、空白、全半角等），再以包含匹配、编辑距离或 Jaro-Winkler 等相似度进行判定。这类方法具有两点优势：一是误报率低、解释性强，二是对“逐字引用”“轻微格式差异”非常有效；其局限则在于难以覆盖学术写作中大量存在的“转述式证据”（同义改写、概括总结、跨句融合）。

第二类是以信息检索与语义表示为核心的相似度匹配（Sparse/Dense Retrieval + Similarity）。传统稀疏检索（如 BM25）擅长利用关键词对齐快速召回候选段落；近年来的稠密检索与句向量方法（如 DPR、SBERT 及其后续工作）在覆盖同义表达方面更具优势，常采用“Top-K 召回 + 阈值过滤/重排序”的两阶段结构。该路线非常适合本项目的闭域论文场景：文本全集可控、可预先切片并建立索引，从而在工程上实现较低的延迟与较稳定的召回。

第三类是事实核验与证据链推理（Fact Verification / Evidence-based QA），典型范式为“检索证据→推理判定（支持/反驳/未知）”。开放域核验强调跨来源检索与证据聚合；而本项目更偏向“闭域核验”，即证据必须来自论文原文切片，因此重点不是“找到外部证据”，而是将上游输出的引用/断言映射回论文原文，并给出可解释的定位与置信度，为下游裁决与人工复核提供依据。

围绕“文本建议去重”，研究与实践则更多关注语义聚类与重复检测：规则去重在表达稳定的场景中有效，但对改写不鲁棒；向量表示 + 聚类（如 DBSCAN、层次聚类）可更好覆盖语义相似，但需要在工程上解决阈值可调、簇代表项选择、以及“去重后仍保留来源链”的可审计性问题。结合本项目多组协作与最终报告可读性的要求，本模块选择在 V1.0 中采用“句向量 + DBSCAN”的工程友好方案，并以簇内成员保留来源追溯。

## （二）研究内容

### 1. 研究目标
本模块面向上游审计 Agent 的结构化输出，承担“把结论落到证据上、把冗余压到可读上”的两类职责。

其一是证据验证（Evidence Validation）：对每条意见中的 `evidence_quote`（逐字引用）或 `claim_text`（摘要式表述）进行闭域核验，判断其是否能在论文原文切片中找到支撑，并输出可解释的定位信息（section/段落/字符区间）与置信度，以支撑前端高亮、反思裁决加权与人工复核触发。

其二是建议去重（Dedup）：将多审计组输出中语义相近的建议进行聚类归并，生成“代表建议 + 证据/来源链”的结构化结果，从而在不丢失可追溯性的前提下提升最终报告的阅读效率与可执行性。

### 2. 研究对象与输入输出
研究对象包含两部分：（1）论文原文内容。该内容由中枢组完成 PDF→Markdown→结构化切片入库，并以 section→paragraph 的层级提供，因此天然支持“以段落为最小证据单元”的定位与高亮。（2）审计组输出的结构化 items。每个 item 至少包含审核点、问题描述、建议与引用证据等字段，本模块以此为输入对象执行核验与去重。

为保证跨组联调一致性，本模块对外输出以“字段少但够用”为原则：证据验证至少返回 `exists`、`method`、`confidence`、`evidence_spans` 与 `matched_text`，并通过 `notes` 解释判定路径（例如“逐字包含（忽略标点）”“语义命中但数字不一致，置信度下调”等），以避免下游把不同来源的分数混为一谈。去重结果则以 `cluster_id`、`representative_item`、`members` 与 `cluster_stats` 为主：其中 members 保留 agent、原始文本与其证据定位，保证“去重后仍可追溯”。

### 3. 关键研究问题
围绕可用性与可信度，本模块重点解决三个问题：第一，如何在闭域论文原文中实现高精度证据定位，同时覆盖逐字引用与同义改写；第二，如何形成可解释、可被下游使用的置信度口径，使反思裁决能“谨慎使用语义匹配结果”而非盲目放大；第三，如何在建议数量波动、表达多样的真实协作场景中实现稳定去重，并保持来源链与证据链的完整性。

### 4. 技术路线

#### 4.1 证据验证：双通道 
证据验证采用“精确优先、语义兜底”的双通道结构。

精确匹配通道首先对 `evidence_quote` 与候选段落进行统一规范化处理，包括但不限于：去除冗余空白、统一全半角、合并连续标点、对常见引号与破折号进行归一化，并在必要时对换行与连字断行做修复。随后以包含匹配为主，并可选引入编辑距离来容忍极小的 OCR/排版误差（例如差异率不超过 2% 时判为命中）。该通道的优势在于“命中即强证据”：一旦命中，可直接输出高置信度（例如逐字包含为 0.97、编辑距离命中为 0.92），并给出字符级定位区间，满足前端高亮与人工复核的快速验证。

语义匹配通道仅在精确未命中时启用，定位为“谨慎兜底”。实现上以段落为最小单元进行向量化表示，并对候选段落执行 Top-K 召回（V1.0 默认 K=5，长文可增至 8），再依据余弦相似度阈值进行过滤（V1.0 默认 `semantic_threshold=0.86`，并预留按领域覆盖的配置口径）。考虑到学术文本中存在大量“泛化句式”（例如“实验结果表明……”“方法有效提升……”）可能造成虚假相似，本模块在阈值通过后再引入轻规则约束以提高精度：当 `claim_text`/`evidence_quote` 含有数字时，要求候选段落包含相同或近似数字格式；当其中含有方法名、数据集名等关键术语时，要求候选段落包含这些关键术语或其可接受的同义变体。置信度采用可解释口径：以相似度为基础分，再乘以规则因子（触发约束则下调），并对语义命中的上限进行封顶（例如不超过 0.90），同时明确标注 `method=semantic`。其目的不是追求“语义命中看起来更高”，而是向下游明确传达：这是兜底结果，应当更谨慎地进入裁决或触发人工复核。

为保证下游可直接使用，证据验证输出在工程上统一为一组最小字段：`exists` 表示证据是否存在；`method` 指示命中通道；`confidence` 体现置信度；`evidence_spans` 返回 section 与段落索引，并提供字符区间，便于前端高亮与复核；`matched_text` 返回命中文本片段以提升解释性；`notes` 记录规范化、阈值、规则触发等信息，便于联调排障与策略回放。这里的关键点在于“定位可复现”：只要论文切片与规范化策略不变，spans 与 matched_text 就应当稳定复现，从而使裁决与报告生成具备可审计性。

需要强调的是，本模块追求的不是单点最强的检索/匹配能力，而是面向联调与可解释性的“最小闭环”：任何命中都必须可定位、可解释、可复核，并且其不确定性要在字段与口径中显式暴露给下游。

#### 4.2 去重聚类：Sentence Embedding + DBSCAN

建议去重采用“句向量 + DBSCAN”的无监督聚类思路。其一，DBSCAN 不要求预设簇数，适合项目联调阶段建议数量起伏较大的真实场景；其二，基于密度的聚类能够将孤立建议自然归为噪声点，避免强行并入不相干簇。实现上，对每条建议文本进行句向量编码，计算余弦距离（$1-\cos$）后执行 DBSCAN，默认参数为 `min_samples=2`、`eps≈0.16`（约对应语义相似度 0.84），并允许在 0.12–0.20 区间小步调参以适配不同写作风格与不同审计组的表述差异。

去重输出强调“归并但不抹除”。因此聚类结果必须同时返回簇代表项与簇内成员列表：代表项用于最终报告的简洁表达，成员列表用于审计追溯与责任归因（哪些组提出过、原始措辞是什么、证据定位在哪里）。代表项的选择采用簇内“平均距离最小”的条目，以兼顾代表性与稳定性；对于跨组来源的簇，还应统计涉及 agent 集合与簇大小，便于反思裁决在报告中给出“多组一致”或“个别组提示”的解释。

#### 4.3 可行性与工程落地
从工程落地角度，本模块具备明确的可行性基础。首先，论文内容已被切片为 section→paragraph 的结构化数据单元，证据定位可直接以段落为检索单元并返回 spans，避免在原始 PDF 上进行复杂定位。其次，算法复杂度可控：精确通道以线性扫描或基于简单索引的匹配即可满足 V1.0；语义通道通过 Top-K 召回限制候选规模，避免对全篇段落暴力比对，从而控制延迟与资源消耗。再次，输出具有天然可解释性：`matched_text` 与 `notes` 能直接在最终报告或前端复核界面呈现“为什么判定命中/不命中”。最后，关键超参数与规则开关均可配置：例如不同领域的 `semantic_threshold`、不同文档长度的 `top_k`、以及去重聚类的 `eps` 与 `min_samples`，均可在联调中通过少量标注样本进行校准。

此外，为降低 PDF→Markdown 过程中排版噪声对精确匹配的影响，V1.0 在文本规范化层面预留了对常见错误的修复：包括但不限于换行断词、连字符断行、表格单元合并导致的空白异常、以及引用符号的多样化。这些工程细节并非“额外功能”，而是保证证据可追溯的必要条件。

#### 4.4 评测设计与验收指标
为使本模块在联调阶段具备明确的“可验收标准”，评测设计坚持两点原则：其一，评测样本必须覆盖真实论文结构与真实审计输出的噪声形态；其二，指标必须能直接反映对下游系统的贡献（减少幻觉进入裁决、提升高亮定位成功率、降低报告冗余）。

证据验证的评测建议采用“小规模人工标注 + 线上回放日志”结合方式。人工标注样本可从不同章节抽取（摘要/方法/实验/讨论/参考文献等），每条样本包含上游 item 的 `evidence_quote` 或 `claim_text`，以及人工确认的“是否存在证据、证据段落位置”。在此基础上，评价指标至少包含：（1）证据存在判定的 Precision/Recall/F1；（2）定位准确率（spans 是否落在人工标注段落，或在容忍窗口内）；（3）解释可用性（matched_text 是否可直接支撑复核）；（4）性能指标（单 paper 的平均耗时与 P95 延迟）。在工程上还应引入“错误类型分布”统计，例如由排版噪声引发的精确不命中、由泛化句式引发的语义误报、由数字不一致引发的规则下调等，便于后续针对性优化。

去重模块的评测可采用“成对一致性 + 聚类质量”双视角：在小样本人工标注中，对建议对（pair）标注“同义/非同义”，计算 pairwise F1；在簇级别统计中，采用簇纯度（purity）与覆盖率（coverage）衡量“去重是否把不同语义错误并入同一簇”以及“同类建议是否被有效聚合”。对于代表项选择，还应进行人工快速检查：代表项是否能覆盖簇内核心行动点，是否会遗漏重要限定条件（例如具体指标、数据集、实验设置）。

#### 4.5 风险分析与对策
本模块的主要风险来自三个方面。第一是文本噪声与对齐风险：PDF→Markdown 的分片过程中可能引入断行、连字符、表格合并等噪声，导致精确通道不命中或 spans 偏移。对策是在规范化层预置对常见噪声的修复策略，并将规范化操作写入 notes，保证问题可回放、可追踪。第二是语义误报风险：语义相似度可能将“泛化描述”误判为证据，进而影响裁决。对策是将语义匹配严格定位为兜底通道，配合轻规则约束与置信度封顶，并将低置信度条目作为人工复核优先队列。第三是去重过度合并风险：不同组的建议看似相近但关键限定条件不同，过度合并会损害信息完整性。对策是以 conservative 的 eps 参数起步，代表项保留关键限定条件，并始终返回 members 以支持追溯与必要时的拆分。

#### 4.6 与接口契约的对齐与边界划分
为降低跨组协作摩擦，本模块明确边界：证据验证只回答“证据是否存在、在哪里、以何种方式命中、可信度如何”，不直接生成新的审计建议；去重只对建议语义相近性做归并，不篡改原始建议的语义指向。所有输出字段需与上游 `/audit` 契约和反思汇总的结构化报告保持一致，尤其是 location 与 spans 的语义一致性（section/段落/字符区间）以及 `notes` 的可解释口径。通过边界划分，能够避免在联调中出现“谁来负责最终口径”的反复拉扯，从而提升整体迭代速度。

### 5. 研究计划
本模块计划与整体联调节奏对齐推进。第一阶段完成证据验证 V1.0 的端到端闭环：从段落切片输入到 `exists/method/confidence/spans` 输出可用，并在 50–100 条覆盖不同章节与不同写作风格的样本上进行自测，重点关注精确命中与定位正确性。第二阶段补齐轻规则约束、置信度口径与 notes 解释，加入单元测试与边界样例（数字一致性、表格数值、跨段落引用、同义改写、OCR 噪声），并与反思裁决共同确认“语义兜底低置信度”触发人工复核的阈值。第三阶段实现去重聚类模块并与报告模板联调，确保代表建议的表达不丢失关键语义，同时 members 保留完整追溯。第四阶段进行集成压测与回归评估，检查在长文档与多组并发情况下的 P95 延迟与稳定性，并形成参数调优建议。

为避免“只写方案不落地”，每一阶段都以可验收产物为目标：可运行的接口、可复现的样本集、以及可解释的输出日志，而非仅停留在方法描述。

## （三）创新之处

本模块的创新并不追求“提出全新算法”，而在于将学术界成熟方法以面向联调、可解释与可审计的方式组合成可落地体系。

首先，在证据核验上提出“闭域双通道最小闭环”：精确匹配承担强证据定位，语义匹配承担对改写/转述的谨慎兜底，并通过统一输出结构将“证据在哪里、为何命中、命中有多可信”标准化为可被下游消费的字段，而不是仅返回一个黑箱分数。

其次，在不确定性管理上引入“规则约束 + 分段置信度口径”。语义匹配天然具有误报风险，本模块不试图用复杂融合掩盖不确定性，而是用数字一致性、关键术语一致性等可解释约束显式下调置信度，并把原因写入 notes，使反思裁决能够对低置信度条目采取更保守的策略（例如降低权重或触发人工复核）。这在协作式多 Agent 评审链路中尤其关键：它使系统具备“知道自己可能错”的自我约束能力。

再次，在报告可读性与审计追溯之间取得平衡：去重聚类以代表项提升可读性，同时保留簇内成员与来源链保证可审计性，使最终报告既能读得快，也能查得清。这一设计直接对齐导师审阅的真实习惯：先看摘要式结论，再根据需要追溯到具体证据与来源。

最后，本模块以配置驱动方式实现跨领域适配。不同学科对证据严谨性的敏感点不同：实验论文对数字一致性更敏感，理论论文对文字改写容忍度更高。将阈值与规则因子外置为配置，有助于在少量标注样本上完成校准，减少后续维护与联调摩擦。

## （四）预期成果

### 1. 成果形式
本模块的交付以“可运行、可联调、可验收”为准。代码层面交付证据验证组件与去重聚类组件，前者支持 exact/semantic 双通道与 spans 输出，后者支持 DBSCAN 聚类、代表项选择与来源链保留；文档层面交付接口字段说明与口径说明，确保与 `/audit` 契约与反思汇总模块一致；测试层面交付覆盖典型边界的单元测试与样例数据集（逐字引用、改写转述、数字不一致、术语缺失、表格数值、OCR 噪声等）；配置层面交付可直接落地的参数模板（`semantic_threshold`、`top_k`、`eps`、`min_samples`、规则开关与下调因子），并形成联调调参记录以便复现实验结论。

### 2. 使用去向
本模块在系统中的使用去向明确：在反思评估组汇总阶段，对各审计组输出的 `evidence_quote` 与关键断言进行二次核验，过滤幻觉引用与错引；在生成最终 Markdown 报告前，对建议进行去重聚类，输出更精炼的“问题—证据—建议”结构，并保留必要的来源链与定位信息以支持追溯。

### 3. 预期效益
预期效益体现在四个层面：第一，可信度提升。通过闭域证据核验显著减少“无证据评语”进入最终报告的比例，使评审结果具备可验证性与可解释性；第二，成本降低。通过置信度口径与规则约束将人工复核聚焦在少量高风险条目（语义兜底、低置信度或规则冲突）上，避免全量复核；第三，可用性提升。通过去重聚类减少重复建议，提升报告信息密度，使关键问题更突出、行动项更明确；第四，联调效率提升。统一 `spans/matched_text/notes` 等字段后，前端高亮定位、反思裁决解释与日志排障更稳定。
